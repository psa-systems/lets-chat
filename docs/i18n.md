# Internationalization (i18n)

lets-chat localizes its server-rendered UI with [Project Fluent](https://projectfluent.org/).
Message catalogs are embedded into the binary at compile time, so the single-file
deploy story is unchanged. This guide covers how the framework fits together and
how to add or edit a translation.

## How it works

- **Catalogs** live at `server/locales/<lang>/*.ftl` (one subdirectory per
  locale). `server/locales/en/main.ftl` is the canonical source: every message
  id used anywhere must exist there, and every other locale must define the same
  ids. English is also the runtime fallback - an unknown locale or a missing key
  renders the English text rather than breaking the page.
- **Embedding**: `fluent-templates::static_loader!` in `server/src/i18n.rs`
  bundles the whole `locales/` tree at build time.
- **Active locale per request**: the `resolve_locale` middleware
  (`server/src/auth.rs`) picks the locale and runs the request inside a
  `tokio::task_local!` (`i18n::CURRENT_LOCALE`). Resolution order:
  1. the signed-in user's saved `users.locale` (set from Settings -> Language);
  2. otherwise the request's `Accept-Language` header;
  3. otherwise English.
  Matching is on the primary language subtag only (region is ignored for now).
- **Templates** localize a string with the `t` filter:
  `{{ "login-title"|t }}`. Plural-aware messages use `tn(count)`:
  `{{ "inbox-unread"|tn(n) }}` (the catalog selects the plural form via the
  Fluent `$count` argument).

  Note the **no space** before the pipe: write `"key"|t`, not `"key" | t`.
  Askama parses `"key" | t` as a bitwise-or expression, not a filter.

- **Filter scope**: Askama generates `filters::t(..)` in the module where a
  `#[derive(Template)]` struct is defined, so each view module that has a
  template using `|t` / `|tn` needs `use crate::i18n::filters;` at the top
  (annotate with `#[allow(unused_imports)]` since only the generated code
  references it).

## Key naming

Fluent message ids cannot contain `.` (that denotes an attribute), so keys are
kebab-case and area-prefixed:

```
login-title = Sign in
settings-language = Language
settings-language-help = Choose the language for the interface.
```

Group related ids under a `## Area` comment header. Keep the English value as the
source of truth.

## Adding a new locale

1. Create `server/locales/<lang>/main.ftl` (e.g. `server/locales/de/main.ftl`).
2. Copy every message id from `server/locales/en/main.ftl` and translate the
   values. The id set must match English exactly - the CI catalog test
   (`server/tests/i18n_catalog.rs`) fails on a missing or stray key.
3. Add the locale's native name to `i18n::native_name` (e.g. `de => "Deutsch"`)
   so it shows nicely in the Settings language picker.
4. `cargo test -p lets-chat-server --test i18n_catalog` to confirm coverage.

Translations are accepted as direct pull requests against the `.ftl` files; there
is no translation platform (Weblate/Crowdin/etc.) yet - revisit if community
translations scale.

## Adding or changing a UI string

1. Add the key + English text to `server/locales/en/main.ftl` (and the
   translation to every other locale, or the coverage test fails).
2. Reference it in the template with `{{ "your-key"|t }}`.
3. Ensure the view module has `use crate::i18n::filters;`.

The CI catalog test guards both directions: a template key with no English
definition fails, and a locale missing an English key fails.

## Scope (v1)

- **UI chrome only.** User-authored content (room descriptions, the LC-96
  login/branding body) is stored as a single string per row and is not
  localized.
- **Out of scope**: right-to-left layout (Arabic/Hebrew); locale-aware date /
  number formatting; localized outbound email templates. These are tracked
  separately.
- WebSocket live-update fragments render outside the request task, so they
  currently fall back to English; full-page loads are localized.
